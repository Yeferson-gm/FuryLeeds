# Flows

Related: [WhatsApp](whatsapp.md) · [Automations](automations.md) · [Inbox](inbox-and-messaging.md) · [Files/media](files-and-media.md)

## Purpose and ownership

Owns stateful deterministic WhatsApp conversation graphs. A flow starts from an inbound trigger, auto-advances through action nodes, suspends for user input, applies fallback policy, records run events, and yields to humans.

## Important source paths

- `src/lib/flows/{engine,types,validate,fallback,repository,meta-send,edges,layout,templates}.ts`
- `src/app/api/flows/**`
- `src/app/api/whatsapp/webhook/route.ts` (runtime dispatch)

## Data model

- `flows`: account/author, `draft|active|archived`, trigger/config, entry node key, fallback JSON, counters.
- `flow_nodes`: unique `(flow_id,node_key)`, type/config JSON and canvas position.
- `flow_runs`: account/contact/conversation, one active run per `(account_id,contact_id)`, current node, vars, reprompt/time/end state.
- `flow_run_events`: ordered audit events: started, node entered, sent, reply, fallback, handoff, timeout, error, completed.
- Supported runtime nodes: start, send message/media/buttons/list, collect input, condition, set tag, handoff, end. Schema also permits `http_fetch`, but runtime/types do not implement it; activation validation should prevent unsupported use.
- Triggers: keyword, first inbound message, manual (manual has no runtime start endpoint).

## API endpoints

| Endpoint | Methods | Access / behavior |
|---|---|---|
| `/api/flows` | GET, POST | Viewer lists; agent+ creates blank/template flow. |
| `/api/flows/:id` | GET, PUT, DELETE | Viewer reads; agent+ transactionally replaces flow/nodes or deletes. |
| `/api/flows/:id/activate` | POST | Agent+; validates graph then activates/deactivates. |
| `/api/flows/:id/runs` | GET | Viewer+; recent runs, contacts and events. |
| `/api/flows/templates` | GET | Viewer+; built-in definitions. |
| `/api/flows/cron` | GET | `CRON_SECRET`; times out stale active runs according to policy. |

## Main flows

- On inbound, newest active run for the account/contact is advanced; otherwise first matching active flow starts.
- Interactive IDs route button/list branches; non-empty text is stored in `vars` for collect-input. Raw captured text is not copied into audit payloads.
- Auto nodes send/interpolate, evaluate conditions over vars/tags/contact fields, mutate tags, then continue in-memory.
- Unknown replies follow `ignore|reprompt|handoff`, reprompt cap and `handoff|end` exhaustion policy.
- Handoff sets conversation pending and optional assignee; agent sends end active runs as `paused_by_agent`.
- Concurrency: Meta-ID duplicate detection, optimistic current-node update, and partial unique active-run index.

## Authorization and tenant boundary

Flow CRUD/run reads include `flows.account_id`/`flow_runs.account_id`. Node rows inherit ownership through an owned flow. Runtime receives the account resolved by WhatsApp config and scopes all contact/conversation/tag reads to it.

## Realtime/events

Flow tables do not emit dedicated socket events. Messages and conversation status/assignment changes generated by a flow emit ordinary thread/conversation realtime events. A consumed inbound suppresses content-level automations and AI, but relationship automations still run.

## Failure modes

- Activation returns structured issues for missing entry, dangling/duplicate edges, invalid Meta limits, unsupported nodes and unreachable nodes.
- Send failures end the run failed (reprompt-send failure is logged but keeps original prompt usable).
- Missing current node, lost optimistic race, unknown node or safety-loop overflow is logged and terminates/ignores safely.
- Duplicate concurrent starts become `duplicate_inbound_ignored`.
- Engine catches unexpected errors and returns unconsumed so other handling can proceed.
- `collect_input.validation` is reserved and currently ignored.

## Tests

`test/lib/flows/{engine,dispatch,fallback,validate,edges,layout}.test.ts` plus component flow-state tests cover trigger text, node classification, graph edges, fallback, validation/reachability and pure engine decisions. DB-heavy end-to-end run advancement is less comprehensive.

## Extension rules

- Add node type to schema check, discriminated union, validator, edge helpers, builder and exhaustive runtime.
- Stable edges use `node_key`, not UUIDs.
- Preserve idempotency/optimistic concurrency and one-active-run invariant.
- Explicitly define whether a node auto-advances, suspends or terminates and how failures end the run.
